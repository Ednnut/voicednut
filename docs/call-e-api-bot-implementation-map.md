# CALL-E API and BOT implementation map

This file records the dependency-aware implementation plan for the ten selected CALL-E-inspired enhancements. Scope is the VOICEDNUT API and Telegram BOT; Mini App work is deferred. The original [integration request](call-e-integration-plan.md) is retained verbatim.

## Contract boundary

VOICEDNUT currently calls CALL-E through its server-side REST client in `api/services/callEClient.js`; there is no CALL-E SDK dependency in `api/package.json`. Checked against the current official docs on 2026-10-31:

- The [Calls API](https://docs.heycall-e.com/calls) supports one phone per `POST /v2/calls`, a required `Idempotency-Key`, persisted reads, cursor-based event pages, and cancellation only before provider submission. It does not support batch recipients, scheduling, or recurrence. The current client implements these documented Calls endpoints.
- The separate [Goals and Goal Runs API](https://docs.heycall-e.com/goal-runs) is also currently supported: published Goals can be listed/read, and each `POST /v1/goals/{goal_id}/runs` creates one phone-specific run with Goal-owned input/result schemas. Goal authoring/publication is not a Developer API operation, and Goal Runs do not provide a batch-call endpoint. VOICEDNUT uses Calls v2 for the existing local-template flow because it supplies per-request task text/schema and no published CALL-E `goal_id` is configured. Goal Runs are a distinct, currently unintegrated resource and are not represented as if they were Calls.
- The official [SDK guide](https://docs.heycall-e.com/sdks) currently documents TypeScript and Python SDK `1.0.1`. This repository follows the existing REST client boundary and does not add a CALL-E SDK dependency. CALL-E API keys remain server-side.
- CALL-E's documented event list includes `call.dtmf`, but no digit value is inferred. CALL-E's current webhook contract is an unsigned terminal notification with a `CALL-E-Event-Id` header matched to the envelope ID; the handler uses the notification only to locate a local call, then reads the authoritative snapshot via the authenticated Calls API before recording a minimal receipt.

Multi-call sequencing, approvals, consent, campaigns, and recovery remain VOICEDNUT orchestration around the documented one-recipient Calls endpoint. No provider endpoint is invented.

## Dependency order

1. **Provider contract and guard baseline:** verify official CALL-E Calls, event, and SDK documentation; keep the existing single-call pilot guard and Twilio/Plivo/Vonage routes intact.
2. **No-call planning and clarification:** planner preview, consent checks, and BOT conversation; validate that planning cannot submit a call.
3. **Result and event normalization:** pin/validate schema, preserve event cursors and DTMF-event presence, expose authorized structured results, and add content-free quality summaries.
4. **Operations and approval:** scoped call history, reconciliation/review/cancel, campaign reports, and distinct reviewer decisions.
5. **Campaign, approval, mission, and execution:** stage a consent-checked campaign from `/callcampaigncreate`, record a separate policy-manager decision, create a mission only from the approved immutable campaign, require a second mission review, then apply exact approval and budget gates, fresh consent/template checks, sequential claims, stable idempotency, and recovery only after both execution and result state are terminal. Paused missions require an audited policy-manager `continue` or `cancel` resolution through `/callmissionresolve`.
6. **Verification:** run focused mock-provider tests, temporary SQLite migration/persistence tests, API/BOT suites, syntax checks, and diff/security review. Any missing runtime dependency is recorded as unverified; it is not replaced by a claimed pass.

## Operational gates and known limits

- `CALLE_MISSION_DISPATCH_ENABLED` defaults to false. Mission execution also requires global CALL-E dispatch/readiness settings, exact mission ID and matching request fingerprint, a current approval reference/expiry, recipient cap, approved database review, and current consent.
- The existing single-call pilot gate remains separate from mission execution. Neither test command nor rehearsal may contact a provider.
- Manual mission advances remain available through BOT/API requests. A new default-off automation worker discovers due scheduled missions and sends each through the same membership, approval, consent, quiet-hours, budget, cooldown, and provider uncertainty checks.
- A paused mission requires `/callmissionresolve <business_id> <mission_id> <continue|cancel>` from a policy manager other than the mission creator and original approver. A `continue` records an idempotent resolution and returns the mission to `running`, but submits no call; the operator must separately use `/callmissionadvance`.
- Campaign and mission creation conversations run only in private BOT chats. They ask for explicit contact authorization, display a reusable idempotency key before submitting, and stage drafts only. Backend consent, four-eyes review, campaign matching, mission fingerprint, and dispatch gates remain authoritative.
- Transcript-based IVR detection is heuristic. DTMF event presence does not establish which key was pressed or whether CALL-E acted on it.
- Follow-on API/BOT enhancements now include optional timezone-qualified mission launch times, mission-level reservation caps in minor currency units, a configurable contact cooldown backed by keyed destination hashes, a one-time review SLA escalation event, and opt-in daily/weekly report digests. `CALLE_MISSION_AUTOMATION_WORKER_ENABLED` defaults to false; mission scheduling also remains behind the exact-mission dispatch and readiness gates. A budget reservation uses an operator-provided per-recipient ceiling and does not guarantee actual provider charges.
- Structured result contents can be business-sensitive. The new direct result path is operator-scoped and BOT display is restricted to private chats; audit retention and role policy still need review before broad rollout.
- Verification on 2026-10-31: `cd api && npm test -- --reporter dot` passed 435 tests, including SQLite-backed mission persistence; the focused mission DB file passed 5 tests; focused CALL-E API mocks passed 38 tests; `cd bot && npm test` passed 4 tests; targeted API ESLint and syntax/diff checks passed. No live CALL-E or telephony requests were made. The API dependency install reported 71 dependency advisories; no audit remediation was attempted as part of this feature work.

## Offline Agent Simulation & Regression Lab

The API adds admin-token protected routes for fixed scenario discovery, versioned runs, and run history: `GET /api/call-scripts/:id/simulation-scenarios`, `POST /api/call-scripts/:id/simulation-runs`, and `GET /api/call-scripts/:id/simulation-runs`. Runs evaluate saved script versions using existing agent-definition/runtime validators, fixed scripted mock-call paths for task completion and approved tool use, deterministic prompt checks, synthetic tool timeout and disallowed-tool attempts, consent-boundary and unsafe-request-refusal checks, escalation fallback checks, and context-injection checks. The mock call provider, scripted agent responder, and tool executor are in-process deterministic fakes; none invokes a model or external provider. These checks exercise policy/runtime paths but do not judge prompt meaning with an LLM. Results are bounded to scenario IDs, scores, codes, and a configuration fingerprint; prompts and transcripts are not saved. A unique `(template_id, idempotency_key)` constraint provides stable replay, and each new run records a comparison with the previous run for that script. Score deltas are withheld when baseline scenario coverage differs.

`GET /api/call-scripts/:id/promotion-readiness` reports whether the currently approved version has a complete, passing Agent Lab run with a matching content fingerprint and score of at least 90%, including status and safe result code for each required scenario. `POST /api/call-scripts/:id/promote-live` enforces the same gate server-side and uses a version precondition to reject content changes between evaluation and promotion. Human script approval and the separate BOT confirmation remain required. The API action bridge applies the same gate.

Every successful promotion now appends an immutable `call_template_promotion_events` record in the same SQLite transaction as demoting the previous live script and promoting the new version. The history records actor label, script version, the passing Agent Lab run/score/fingerprint, timestamp, and prior live script/version. `GET /api/call-scripts/:id/promotion-history` is admin-token protected; events remain readable by script ID after script deletion. The BOT carries its Telegram numeric user ID as the actor label and exposes an interactive **Promotion history** action. Existing rollback remains an interactive, confirmed snapshot restore to draft, so it must pass review and Agent Lab again before returning live. Other admin API clients may supply `x-admin-user`; with the current shared admin-token model that value is a caller-supplied label, not a separately verified identity.

The scripts detail menu exposes **Agent Lab** as an interactive BOT workflow. Operators choose a current or saved version, see recent scores, and must type `RUN OFFLINE SIMULATION` before submitting. It displays scenario outcomes, comparable baseline deltas, and zero model/provider request counts. A read-only **Readiness** view and the promotion flow show the full scenario matrix, score threshold, suite coverage, fingerprint status, evaluation run, and blockers together; promotion then requires a separate confirmation when the API gate passes. The simulator does not execute an AI model, contact Twilio, Plivo, Vonage, CALL-E, or place a call. The scripted actor's completion score verifies the configured tool gate and deterministic mock lifecycle; it does not measure generated speech, LLM interpretation, or real-world conversation quality. The new table is additive and initialized with the existing SQLite schema setup.

When recent Agent Lab results contain failures, the BOT offers a focused rerun of those scenario IDs against the selected version, alongside a full-suite option. API results expose `evaluation_scope` (`focused` or `full_suite`) and `complete_suite`. Focused runs remain visible and useful for iteration, but promotion readiness cross-checks both the stored selected scenario IDs and result coverage and rejects incomplete runs. After script edits, operators must run the full suite again before promotion.
